📖 Rust Book Reading Map for T1Diaries

Which sections of "The Rust Programming Language" (the official Rust Book, current edition at doc.rust-lang.org/book) to read before implementing each part of the T1Diaries backend — so you learn concepts exactly when you're about to use them, instead of front-loading the whole book.

Source: doc.rust-lang.org/book Companion to: Repo Template Build Guide
How to use this document: it is ordered to match the Build Guide's steps 1–15, not the book's own chapter order. Each entry names the exact chapter(s)/section(s), a one-line summary of what's in them, and — most importantly — why that chapter matters for the specific piece of code you're about to write. You do not need to read the book cover to cover before starting; read each row right before the matching build step.

Before Phase 0 — Scaffolding & workspace (Build Guide Steps 1–2)

Ch.1 — Getting Started

Installing rustup, your first cargo new, cargo build/run. Read fully if this is your first Rust project.

Ch.3 — Common Programming Concepts

Variables/mutability, data types, functions, comments, control flow (if, loop, match preview). Skim if you know a C-like language already; read fully otherwise.

Ch.4 — Understanding Ownership critical

Ownership, references & borrowing, the borrow checker, slices. This is the Rust concept — you will hit borrow-checker errors the moment you write your first &self method, and this chapter is the only thing that makes those errors make sense instead of feeling arbitrary.

Ch.7 — Packages, Crates, and Modules critical

The exact vocabulary of what you're building in Step 2: a package (one Cargo.toml) can contain multiple crates; a workspace groups multiple packages; mod/pub control visibility (this is why crates/graphql can see t1diaries_auth::graphql::AuthQuery but not its private repository internals).

Before Phase 1 — Auth (Build Guide Step 7)

This is the densest step in the whole build guide, and correspondingly needs the most reading. Read these in order before opening crates/auth:

Ch.5 — Structs

UserRecord, SignUpInput, Claims — every DTO in the auth flow is a struct. Pay attention to the section on methods (impl blocks) — AuthService's methods are defined exactly this way.

Ch.6 — Enums and Pattern Matching

AppError is an enum; match on it (as in the GraphQL error-extension mapping) is exhaustive-checked by the compiler — read the section on match and the Option<T> enum specifically, since find_by_email returns Option<UserRecord>.

Ch.9 — Error Handling critical

The Result<T, E> type, the ? operator (used in nearly every line of repository.rs and service.rs), and when to panic! vs. return Result. This chapter is the direct justification for the AppError/ AppResult<T> pattern from Build Guide Step 3.

Ch.10 — Generics, Traits, and Lifetimes critical

Traits are how AuthRepository is defined as an interface with a Postgres implementation (PgAuthRepository) swapped in — read the "Traits as Parameters" and "Trait Objects" framing carefully; it's the exact shape of Arc<dyn AuthRepository>.

Ch.13.2 — Closures

Short section, but the token-claims construction and iterator-based row-mapping (later, in blogs/devices) use closures constantly — |r| Device { ... } in Step 8 is a closure.

Ch.15 — Smart Pointers critical

Focus on Box<T> and Rc<T> (shared ownership) — this is the mental model behind Arc<dyn AuthRepository> and Arc<dyn EmailSender> in AuthService (Arc is Rc's thread-safe sibling, introduced in the next chapter).

Ch.16 — Fearless Concurrency

Read 16.1–16.3 (threads, message passing, shared state via Mutex<T>/Arc<T>). You won't spawn raw OS threads in this project, but this chapter is the prerequisite for understanding why Arc exists and why cloning a PgPool or a service is cheap and safe across concurrent axum requests.

Ch.17 — Fundamentals of Asynchronous Programming critical

Futures, async/.await, and why an async runtime (tokio) is needed. Every function in AuthService, every axum handler, and every async-graphql resolver is an async fn — this chapter explains what that actually means under the hood (a suspended state machine polled by tokio), not just the syntax.

Ch.18 — Object-Oriented Programming Features

Specifically the "Using Trait Objects That Allow for Values of Different Types" section — this is the formal explanation of the dyn AuthRepository pattern used throughout AppState.

async-trait note: the code in Build Guide Step 7 uses the #[async_trait] macro from the async-trait crate to put async fn inside a trait — native async fns in traits landed in stable Rust but still have limitations with trait objects (dyn Trait), which is exactly what Arc<dyn AuthRepository> needs. The Rust Book's Ch.17/18 explain the underlying "why," but the crate itself isn't covered in the book — its docs on crates.io are the reference for the macro's exact behavior.

Before Phase 2 — Users/Profile

No new chapters — Phase 2 reuses the exact struct/trait/error/async patterns from Phase 1. This is a good point to re-skim Ch.9 and Ch.10 if the auth code didn't fully click the first time; writing the same pattern a second time for a new domain is often when it actually sinks in.

Before Phase 3 — Blogs (posts & comments)

Ch.8 — Common Collections critical

Vec<Post>, Vec<Comment>, tag lists, and building comment trees (parent/child) all lean on Vec and HashMap — read the HashMap section specifically before implementing comment-thread grouping (grouping comments by parent_comment_id).

Ch.13 (full) — Iterators and Closures critical

Cursor-based pagination, DataLoader batching, and comment-tree building are all naturally expressed as iterator chains (.filter(), .map(), .collect(), .fold()) — read the full chapter this time, not just the closures section from Phase 1.

Before Phase 4 — Stats (background jobs, scraping)

Ch.16 (re-read fully) — Fearless Concurrency

The stats ingestion job runs on a schedule, independent of any HTTP request — read 16.1 (thread::spawn) again, now thinking about its async cousin, tokio::spawn, which is what actually runs the periodic scraper alongside the axum server in the same process.

Ch.17 (re-read) — Async fundamentals

Specifically anything on running multiple futures concurrently — the scraper fetches from several external sources; understanding join!/concurrent futures (covered conceptually here, with tokio-specific APIs in tokio's own docs) avoids writing an accidentally-sequential scraper.

The book teaches async fundamentals but not tokio's specific scheduler APIs (tokio::spawn, tokio::time::interval) or a cron-style crate like tokio-cron-scheduler — once Ch.17's concepts click, go to tokio's own documentation for the concrete scheduling API used in the background job.

Before Phase 5 — Devices (read-mostly domain)

No new chapters required — by this point you've written the repository→service→graphql pattern three times (auth, users, blogs). Devices is the simplest of the four domains (query-only), so it doubles as a good self-check: if you can write it without re-reading anything, Ch.9/10/13 have become comfortable.

Before Phase 6 — Hardening (concurrency, tracing, production)

Ch.16.3 — Shared-State Concurrency

Mutex<T> and Arc<Mutex<T>> — relevant if you implement in-memory rate limiting or counters rather than pushing that entirely into Redis.

Ch.11 — Writing Automated Tests

#[test]/#[should_panic], organizing unit vs. integration tests (tests/ directory per crate) — read before Build Guide Step 14 if you skipped it earlier.

Ch.20 — Advanced Features (skim)

The sections on advanced traits (associated types) and a conceptual intro to macros help demystify what #[derive(SimpleObject)], #[Object], and sqlx::query_as! are doing ��� they're procedural macros generating code at compile time, which this chapter introduces at a basic level (the book does not cover writing your own proc macros in depth).

Ch.21 — Final Project: Multithreaded Web Server

If you skipped this before Step 10, read it now with fresh eyes: you'll recognize axum's Router/listener/handler flow as a productionized version of exactly what this chapter builds by hand (TCP listener → parse request → route → thread pool → response).

A note on GraphQL macros vs. "plain" Rust

The Rust Book does not cover async-graphql, axum, or sqlx — it teaches the language itself. Once you understand why traits, generics, and async/await work the way they do (Ch.9, 10, 17, 18), the following crate-specific patterns become readable as "just" applications of those concepts rather than new magic:

Pattern you'll see in code Book concept it's built on
#[derive(SimpleObject)] on a struct Ch.5 (Structs) + Ch.20 (macros, conceptually)
#[Object] impl AuthMutation { async fn ... } Ch.5 (impl blocks) + Ch.17 (async fns)
ctx.data::<AuthService>()? Ch.10 (generics — data::<T> is a generic method) + Ch.9 (the ? operator)
Arc<dyn AuthRepository> Ch.15 (smart pointers) + Ch.18 (trait objects)
sqlx::query_as!(...) Ch.20 (macros) — a compile-time-checked SQL macro; the SQL itself isn't a Rust Book topic
#[derive(MergedObject)] Ch.7 (modules — this is literally module composition, expressed as a derive macro)

Chapters you can skip or skim for this project

  • Ch.2 — Programming a Guessing Game. A standalone learning exercise; nothing here is reused directly in T1Diaries. Skip if you already know another programming language.
  • Ch.12 — I/O Project (minigrep). Good practice for structuring a small CLI, but T1Diaries has no CLI component — skip unless you want the extra exercise.
  • Ch.14 — More About Cargo and Crates.io. Covers release profiles and publishing to crates.io; the workspace-specific parts you need are already covered directly in the Build Guide. Skim only if curious about custom build profiles.
  • Ch.19 — Patterns and Matching (deep dive). A reference chapter expanding on Ch.6; read it only if you hit a pattern-matching construct (e.g. @-bindings, match guards) that Ch.6 didn't cover.
