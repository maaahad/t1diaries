1. Monorepo philosophy — why this layout

Large engineering orgs (Shopify's Rust services, Discord's Rust rewrite of Read States, Figma's multiplayer server, 1Password's backend) converge on the same shape for a Rust+GraphQL+React product: a single repo split into two independently-buildable workspaces glued together by a generated contract:

Cargo workspace (Rust)

One Cargo.toml at the root declares [workspace] members. Each bounded context (auth, blogs, stats, devices, users) is its own library crate, compiled independently, tested in isolation, and composed only at the binary crate (apps/api).

pnpm/Turborepo workspace (JS)

The frontend and any shared JS packages (design system, generated GraphQL types, ESLint config) live under apps/ and packages/, orchestrated by pnpm workspaces + Turborepo for cached, parallel builds.

The GraphQL schema is the contract

The Rust API is the single source of truth for the schema (SDL). The frontend runs graphql-code-generator against it to produce fully-typed hooks — no hand-written fetch logic, no drift between backend and frontend types.

Why not one giant crate / one giant React app? Splitting into crates and packages gives you (1) parallel compilation, (2) enforced boundaries — blogs cannot reach into auth's internals, only its public API, (3) the ability to unit-test a domain without booting a database or an HTTP server, and (4) a place to eventually extract a crate/package into its own service if the product grows.

Naming convention: Rust crates live under crates/<domain> and are named t1diaries-<domain> in Cargo.toml (e.g. t1diaries-auth) to avoid collisions on crates.io-style tooling and to make cargo doc output unambiguous.

4. Backend: Cargo workspace & crate breakdown

Every crate below is a library crate except apps/api, which is the only binary. This means domain crates are unit-testable with cargo test -p t1diaries-blogs without ever starting an HTTP server.

crates/config

Loads .env / environment variables into a strongly-typed AppConfig (database URL, JWT secret, Redis URL, SMTP creds, port). Fails fast at boot if something required is missing.

crates/error

Defines the crate-agnostic AppError enum and a single place where domain errors are converted into async_graphql::Error (with error codes/extensions) — so every resolver returns errors consistently to the frontend.

crates/db

Owns the sqlx::PgPool construction, the migration runner, and small generic helpers (pagination cursor encode/decode, "not found" mapping). Domain crates depend on this but never construct their own pool.

crates/cache

Owns the Redis connection pool (via deadpool-redis) used for: refresh-token storage, email-verification/reset tokens with TTL, and caching the (expensive, externally-sourced) stats payload.

crates/auth

Signup, signin, signout, verify-email, forgot/reset-password, and the JWT + refresh-token issuing/validation logic. Exposes an AuthService trait + Postgres implementation, and an axum Extractor (CurrentUser) other crates/resolvers use to get "who is calling".

crates/users

User profile CRUD (display name, avatar, T1D diagnosis year/type, bio), role management (member/moderator/ admin), and the repository trait for looking up users by id/email — used by auth too.

crates/blogs

Posts (draft/published/archived), tags, and threaded comments. Contains its own service layer + repository, independent of how GraphQL exposes it.

crates/stats

Domain model for T1D statistics (prevalence, incidence, regional breakdowns, source/citation, collected_at). Includes a background job (StatsRefreshJob) that periodically scrapes/ingests external sources and upserts normalized rows.

crates/devices

Catalog of T1D-related devices (CGMs, insulin pumps, closed-loop systems): manufacturer, model, category, release_date, region_availability, specs (JSONB), and a "latest" query sorted by release date.

crates/email

Thin wrapper over lettre exposing EmailSender trait (so it's mockable in tests) — sends verification links, password-reset links, comment-reply notifications.

crates/graphql

The composition root for the API surface. Contains no business logic — only resolver structs that call into each domain crate's service layer and shape the response into GraphQL types. See section 5.

apps/api

main.rs only: reads config, builds the pool/cache/services, builds the async-graphql Schema, wires the axum Router (GraphQL endpoint, GraphiQL playground, health check, middleware stack), and calls axum::serve.

5. The "thin" GraphQL layer pattern

The core architectural rule: crates/graphql never talks to the database directly, never hashes a password, never sends an email. It only:

  1. declares the GraphQL shape (types, inputs, field names) with async-graphql derive macros,
  2. extracts dependencies (services) from GraphQL Context,
  3. calls a single method on a domain service, and
  4. maps the result/error into the GraphQL type.

All actual logic — validation, hashing, SQL, transactions — lives in the domain crate's service.rs. This keeps resolvers testable-by-inspection (they're 5–10 lines each) and lets you unit test business logic without spinning up a GraphQL schema at all.

Query/Mutation modularization

Each domain crate exports its own Query and Mutation struct (e.g. AuthMutation, BlogQuery, BlogMutation, StatsQuery, DeviceQuery, UserQuery). crates/graphql merges them with async-graphql's #[derive(MergedObject)] into one root Query and one root Mutation:

crates/graphql/src/schema.rs 
use async_graphql::{EmptySubscription, MergedObject, Schema};

          use t1diaries_auth::graphql::{AuthMutation, AuthQuery};
          use t1diaries_blogs::graphql::{BlogMutation, BlogQuery};
          use t1diaries_devices::graphql::DeviceQuery;
          use t1diaries_stats::graphql::StatsQuery;
          use t1diaries_users::graphql::{UserMutation, UserQuery};

          use crate::state::AppState;

          #[derive(MergedObject, Default)]
          pub struct RootQuery(AuthQuery, UserQuery, BlogQuery, StatsQuery, DeviceQuery);

          #[derive(MergedObject, Default)]
          pub struct RootMutation(AuthMutation, UserMutation, BlogMutation);

          pub type AppSchema = Schema<RootQuery, RootMutation, EmptySubscription>;

          pub fn build_schema(state: AppState) -> AppSchema {
          Schema::build(RootQuery::default(), RootMutation::default(), EmptySubscription::default())
          .data(state.auth_service)
          .data(state.user_service)
          .data(state.blog_service)
          .data(state.stats_service)
          .data(state.device_service)
          .finish()
          }
Each domain crate ships its own graphql module (e.g. t1diaries_blogs::graphql) containing query.rs (read resolvers) and mutation.rs (write resolvers) — so "modularize mutation and query" happens twice: once per-domain (query vs mutation files) and once again at the root (per-domain merge). Full code is in the Build Guide document, Step 7.

6. Domain breakdown

6.1 Auth (crates/auth)

Operation GraphQL shape Notes
Sign up mutation signUp(input: SignUpInput!): AuthPayload! Validates email/password (via validator), hashes with argon2, inserts user (unverified), sends verification email, issues short-lived access token + refresh token.
Sign in mutation signIn(input: SignInInput!): AuthPayload! Verifies password hash, blocks unverified accounts (configurable), issues tokens.
Sign out mutation signOut: Boolean! Revokes the refresh token server-side (deletes from Redis) and clears the httpOnly cookie.
Verify email mutation verifyEmail(token: String!): Boolean! One-time token (stored in Redis with TTL) sent by email; marks users.email_verified_at.
Forgot password mutation requestPasswordReset(email: String!): Boolean! Always returns true (no user enumeration) — silently no-ops if email unknown.
Reset password mutation resetPassword(token: String!, newPassword: String!): Boolean! Validates reset token, re-hashes password, revokes all existing refresh tokens for that user.
Refresh token mutation refreshToken: AuthPayload! Reads refresh token from httpOnly cookie, rotates it, issues a new access token.
Current user query me: User Returns null if unauthenticated rather than erroring, so the frontend can render logged-out states cleanly.

Authorization (as opposed to authentication) is implemented as a small Guard (async-graphql supports field-level guards) checking the CurrentUser's role — e.g. only Moderator/Admin can delete another user's comment.

6.2 Users (crates/users)

Profile fields relevant to a T1D community: display name, avatar URL, diabetes type (T1/LADA/other), year of diagnosis, country/region, short bio, and privacy flags (e.g. hide diagnosis year publicly). Resolvers: query user(id), query users(cursor, filter), mutation updateProfile(input), mutation updateRole(userId, role) (admin-only, authorization-guarded).

6.3 Blogs (crates/blogs)

Entity Key fields
posts id, author_id, title, slug, body (markdown), status (draft/published/archived), tags[], published_at, created_at, updated_at
comments id, post_id, author_id, parent_comment_id (nullable, for threads), body, created_at, edited_at, is_deleted (soft delete)

Resolvers: query post(slug), query posts(cursor, tag, authorId) (cursor-based pagination via async-graphql's connection module), mutation createPost, mutation updatePost, mutation publishPost, mutation addComment, mutation deleteComment. Comment counts / author info are resolved via async_graphql::dataloader::DataLoader to avoid N+1 queries when listing many posts.

6.4 Stats (crates/stats)

Read-only from the GraphQL API's perspective (no user can mutate statistics) — populated by a background job. Model: stat_snapshots (metric_key, value, unit, region, source_url, collected_at). Resolvers: query globalStats (latest snapshot per metric), query statHistory(metricKey, region) for trend charts. The scraper job (in the same crate, run via a small worker binary or a scheduled task inside apps/api) fetches from public sources (e.g. IDF Diabetes Atlas, CDC, JDRF), normalizes, and upserts — the GraphQL layer is decoupled from where the numbers came from.

6.5 Devices (crates/devices)

Model: devices (id, name, manufacturer, category [CGM/pump/closed-loop/pen], release_date, regions[], specs JSONB, image_url, description). Resolvers: query devices(cursor, category), query latestDevices(limit) (ordered by release_date DESC), query device(id). Write access (adding/curating devices) is admin-only, gated by the same role guard as user role updates.

Each features/<name> folder mirrors a backend domain crate 1:1 — the same mental model crosses the stack: auth ↔ crates/auth, blog ↔ crates/blogs, etc. This is the same "vertical slice" convention used in Nx/Turborepo React monorepos at companies like Vercel and Cal.com.

packages/graphql-client

Holds the generated TypeScript types + typed hooks (output of graphql-code-generator using the typescript, typescript-operations, and typescript-react-query plugins) plus a single configured graphql-request client instance (base URL, auth header injection, cookie credentials). Every feature imports from here instead of writing its own fetch call.

packages/ui

Tailwind-based design system primitives (Button, Input, Card, Modal, Toast) built once, consumed by every feature — keeps visual consistency and avoids each feature re-implementing form controls.

9. Infra, CI/CD, and environments

Local development

infra/docker-compose.yml brings up Postgres, Redis, and Mailhog (fake SMTP UI at localhost:8025). cargo watch -x run auto-reloads the API; pnpm dev (via Turborepo) starts the Vite dev server with the API proxied.

CI (GitHub Actions)

Two parallel jobs: rust (spin up Postgres service container → sqlx migrate run → cargo fmt --check → cargo clippy -- -D warnings → cargo test --workspace) and web (pnpm install --frozen-lockfile → turbo lint test build). A third job diffs the exported GraphQL SDL against the committed schema file to catch accidental breaking changes.

Deployment shape

apps/api compiles to a single static-ish binary → multi-stage Dockerfile (build stage with cargo chef for layer caching, slim runtime stage e.g. debian-slim or distroless). apps/web builds to static assets served via a CDN/edge host (Vercel/Netlify/Cloudflare Pages) or bundled behind the same reverse proxy as the API.

Migrations in CI/CD

sqlx migrate run executes as a release step before the new API version receives traffic (or via an init-container in k8s). sqlx's "offline mode" (cargo sqlx prepare) lets cargo build succeed in CI without a live database, by checking compile-time query metadata into .sqlx/.

Cargo workspace + pnpm workspace created, empty crates compiling, Docker Compose up, CI pipeline green on an empty "hello" schema. Deliverable: a booting axum server with a GraphiQL playground and a Vite app that can query it.

4
